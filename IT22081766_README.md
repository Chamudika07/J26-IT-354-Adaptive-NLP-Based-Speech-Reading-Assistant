# Adaptive NLP-Based Speech & Reading Assistant for Children with Dyslexia

**Project ID:** J26-IT-354

**Student ID:** IT22081766

**Project type:** University research and software engineering project

**Current stage:** Backend prototype with implemented reading workflows; mobile application pending

This project investigates how natural language processing and accessible software
can support children who experience reading difficulties associated with dyslexia.
The intended system brings reading materials, educational reading observations,
and future speech and adaptation capabilities into one application.

The current repository implements a shared backend for authentication, learner
access, instructor-observed reading assessments, English text processing, and
machine-readable PDF extraction. The project title describes the broader research
direction; speech assistance and automated adaptation are not yet implemented.
Educational measurements are not medical diagnoses.

## Project objectives

- Provide a consistent backend for learner profiles and authorized educational support.
- Record instructor-observed reading performance with explicit scoring conventions.
- Prepare English reading materials and expose transparent text measurements.
- Preserve material versions and extraction evidence for traceability.
- Establish a testable foundation for future speech and adaptive reading research.

These are engineering and research objectives, not claims of clinical effectiveness
or demonstrated improvements in learning outcomes.

is suitable for an individual learner. Scanned PDFs cannot currently be converted
through a deployed OCR workflow. An `ocr_required` extraction outcome does not mean
OCR has been performed.

## Architecture

The application follows a **modular monolith**: one shared FastAPI backend at
`apps/backend` and one PostgreSQL application database per environment. REST
endpoints use the `/api/v1` prefix.

```text
API consumers / Swagger UI          Future mobile application
            |                                |
            +----------- /api/v1 ------------+
                             |
                    Shared FastAPI backend
            Auth | Learners | Assessments | Reading materials
                             |
                 Shared SQLAlchemy infrastructure
                             |
                     PostgreSQL database
                   One Alembic migration history
```

Modules own their tables and expose service interfaces for cross-module work.
Pydantic request/response schemas are separate from SQLAlchemy persistence models.
Database records use UUID keys and timezone-aware UTC timestamps. Schema changes
use explicit Alembic migrations; startup does not create tables automatically.

PDF binaries use private filesystem storage, with references and extraction evidence
in the shared database. Research experiments have separate dependencies and are not
imported by production code.

## Getting started

### Prerequisites

- Git and a local checkout of this repository.
- Docker with Compose v2 or newer and a running Docker daemon.
- Python 3 for the secret-generation command below.
- For host development and quality checks: Python 3.13 and uv 0.12.23,
  matching the repository CI configuration.

Node.js and React Native tooling are not required at this stage. Run the following
commands from the repository root unless another directory is specified.

### Option A: Run with Docker

Set a local URL-safe database password and generate a signing key. Replace the
password placeholder before running the commands. For an existing database volume,
use its existing password.

```sh
export POSTGRES_PASSWORD='replace_with_your_own_url_safe_password'
export JWT_SIGNING_KEY="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
docker compose up --build -d --wait
docker compose exec backend alembic upgrade head
curl http://127.0.0.1:8000/api/v1/health
curl http://127.0.0.1:8000/api/v1/health/ready
```

Expected responses are `{"status":"ok"}` and `{"status":"ready"}` respectively.
Readiness verifies database connectivity; it does not prove that migrations or
business workflows are complete. Apply migrations explicitly as shown above.

Open **[Swagger UI](http://127.0.0.1:8000/docs)** to inspect and exercise the API.
The local Compose services bind to `127.0.0.1`; this configuration is for development.

Useful commands:

```sh
docker compose ps
docker compose logs backend
docker compose exec backend alembic current
docker compose stop
```

`docker compose stop` preserves containers and local data. `docker compose down`
removes containers but preserves the named database volume. Adding `-v` deletes
that volume and its database data. Changing initialization variables does not reset
an existing database password.

### Option B: Run the backend on the host

Start the same Compose database and run FastAPI locally. If the Compose backend
is already running, stop it first with `docker compose stop backend` to free port 8000.

```sh
export POSTGRES_PASSWORD='replace_with_your_own_url_safe_password'
export JWT_SIGNING_KEY="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
docker compose up -d --wait db
cd apps/backend
uv sync --locked
export DATABASE_URL="postgresql+psycopg://adaptive:${POSTGRES_PASSWORD}@127.0.0.1:5432/adaptive"
uv run --locked alembic upgrade head
uv run --locked uvicorn app.main:create_app --factory --reload --no-access-log
```

This example assumes the default database name, user, and port. Adjust the URL if
those settings change. Use URL-encoded credentials when they contain reserved
characters. Optional PDF storage requires Linux/macOS filesystem support; see the
[PDF extraction guide](docs/pdf-text-extraction.md) for runtime requirements.

## Configuration

The root [`.env.example`](.env.example) documents Compose settings;
[`apps/backend/.env.example`](apps/backend/.env.example) documents backend settings.
Exported environment variables work without creating a `.env` file.

| Variable | Purpose |
| --- | --- |
| `POSTGRES_PASSWORD` | Required local Compose database password |
| `JWT_SIGNING_KEY` | Required cryptographically random signing secret of at least 32 bytes |
| `DATABASE_URL` | Backend PostgreSQL connection URL; supplied by Compose or exported for host execution |
| `APP_ENV` | Runtime environment; local Compose defaults to `development` |
| `POSTGRES_PORT` / `API_PORT` | Local Compose ports; defaults are `5432` / `8000` |
| `PDF_STORAGE_ROOT` | Optional absolute private storage directory required for PDF operations |
| `TEST_DATABASE_URL` | Exclusive disposable PostgreSQL database for integration tests |
| `ALLOW_TEST_DATABASE_RESET` | Set to `1` only when authorizing resets of that disposable test database |

Keep credentials private and reuse the intended local signing key across restarts;
changing it invalidates previously signed access tokens. Never commit real `.env`
files or secrets.

The default Compose setup does not provision PDF storage. PDF operations require
an appropriately owned private directory, a container mount when applicable, and
`PDF_STORAGE_ROOT` passed to the backend. Follow the
[PDF setup instructions](docs/pdf-text-extraction.md) before demonstrating uploads.

## API demonstration

A fresh database has no default login credentials or public registration endpoint.
Accounts, learner access grants, and assessment materials require appropriate
internal provisioning; migrations do not seed demo users or assessment passages.

For a demonstration without an account:

1. Start the services and apply migrations.
2. Open Swagger UI and execute `GET /api/v1/health` and `GET /api/v1/health/ready`.
3. Execute `GET /api/v1/learners` without a token to demonstrate HTTP `401` protection.
4. Inspect the authentication, learner, assessment, and reading-material schemas.

For authenticated workflows, use a provisioned **synthetic** account and synthetic
learner records. Log in through `POST /api/v1/auth/login`, then paste the returned
access token into Swagger's **Authorize** bearer field. Access also depends on the
account's current learner-level grants. Do not display passwords or token responses
in a recorded or projected presentation.

## Testing and quality checks

From the repository root, run:

```sh
sh scripts/check_backend.sh
```

The script synchronizes locked dependencies and runs Ruff linting, formatting
checks, strict mypy checks, and pytest with coverage reporting.

Tests that do not require a database use synthetic configuration. PostgreSQL tests
require an exclusive disposable database whose name ends in `_test`, an explicit
`TEST_DATABASE_URL`, and `ALLOW_TEST_DATABASE_RESET=1`. They can drop and recreate
application tables and never fall back to `DATABASE_URL`. Without the test database
configuration, database-dependent tests are skipped.

Follow the [database test setup guide](docs/database-sprint-1.md) to run the complete
suite locally. Never use a shared or production database for tests. The
[CI workflow](.github/workflows/ci.yml) provisions isolated PostgreSQL, runs checks,
applies migrations, checks schema drift, validates Compose, and builds the image.
This describes the configured checks, not a claim that a particular run has passed.

## Privacy and research boundaries

- Use synthetic learner data in development, tests, and demonstrations.
- Enforce learner-level authorization for access to learner information.
- Collect only the learner information needed by the supported workflow.
- Keep recordings, datasets, database dumps, model checkpoints, and credentials out of Git.
- Do not log credentials, tokens, learner content, or complete settings.
- Keep research dependencies separate and document provenance before promoting research code.
- Present reading scores as educational observations, never as diagnoses or clinical severity estimates.
