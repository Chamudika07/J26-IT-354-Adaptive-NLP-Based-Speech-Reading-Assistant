# Database Sprint 1

This sprint implements storage and data contracts only. No authentication endpoints,
login flow, relationship authorization service, consent-policy evaluator, mobile UI,
or reading/speech/analytics/numeracy behavior has been added.

## Migration chain

- 0001_foundation: unchanged original baseline.
- 0002_auth_identity: users, roles, user_roles; four fixed UUID role definitions only.
- 0003_learner_foundation: learner_profiles, guardian_learner_relationships,
  educator_learner_relationships, learner_preferences.
- 0004_consent_evidence: consent_notice_versions, consent_records.

One shared Base/metadata and one Alembic history remain. Migrations are frozen schema
snapshots; they never import current application models. Mutable ORM records use
row_version optimistic concurrency. IDs are UUIDv4 generated by SQLAlchemy; callers
using raw SQL must supply their own UUIDs. Timestamps use PostgreSQL timestamptz and
UTC connections. No PostgreSQL native enums or JSONB columns are introduced.

Age_band is an optional SMALLINT value in 9..12 and grade_level is an optional
SMALLINT value in 3..8, as approved. Neither is derived from or accompanied by an exact
birth date. No diagnosis, severity, clinical history, national ID, or home address is
stored. User email and learner login links remain optional; only one profile can use
a given personal login. A creator reference is provenance, not authorization.

## History and privacy boundaries

Database triggers reject changes to identity/provenance fields, grant payloads, closed
grant revocation fields, and published notice wording. A role code is immutable.
Notices may be retired but cannot be reopened or rewritten. Consent events reject
UPDATE, DELETE, and TRUNCATE. Append a new decision instead of editing prior evidence.
Only roles are seeded; consent text must come from a later approved publication flow.

The notice SHA-256 digest is checked against its exact UTF-8 text using PostgreSQL's
built-in sha256 function; no extension is required. Notice and guardian composite FKs
keep consent purpose/kind and learner scope consistent. NULLS NOT DISTINCT uniqueness
protects learner-assent sequence numbers even without a guardian relationship.

Historical FKs use RESTRICT. Deleting a personal login uses SET NULL on its learner
profile; deleting an authorized learner profile cascades only its preference row.
The catalog below lists every FK. Revocation/archiving is operational lifecycle, not
an erasure guarantee. A retention process is deferred and must use a separate,
privileged, reviewed path; an application role must not own tables or be allowed to
alter/disable triggers. Owners/superusers can override these protections.

The current development Compose database role is privileged for local convenience.
Least-privilege runtime/migration roles must be provisioned before deploying or using
real learner data. Database permission provisioning is not performed by these migrations.

## Deferred service responsibilities

- Account/role/learner status, educator expiry, per-action relationship permissions,
  verified guardian authority at consent time, and multi-guardian conflicts must be
  checked by future owning services. FKs do not implement authorization.
- Educator expiry is checked against created_at structurally. Effective access must
  also test expires_at against the current time. Expired unrevoked grants still block
  replacements until explicitly closed; no time-dependent index predicate is used.
- Consent sequence allocation must lock the learner row and allocate within its stream;
  the database unique constraint prevents duplicates but does not allocate sequences.
- Capture self-service occurred_at using the database clock; it must not exceed
  recorded_at. Host/client clocks can differ. Assisted historical times need validation.
- Role revocation/account retirement must coordinate related grants through the owning
  services; no cross-module write or automatic access propagation has been introduced.
- Optimistic counters apply to ordinary ORM updates. Bulk/raw SQL needs explicit version
  predicates, counter increments, and timestamp updates. Last-editor fields are not a
  complete audit history. FK SET NULL does not itself increment row_version.
- Preference ranges are UI assumptions, not diagnostic or clinical recommendations.

## Verification and local test environment

Python 3.13, PostgreSQL 17, the existing locked backend dependencies, and Docker are
used. No new dependencies were needed. Unit tests need no PostgreSQL. Integration
and migration tests require TEST_DATABASE_URL (postgresql+psycopg, database ending
in _test) and ALLOW_TEST_DATABASE_RESET=1. The latter explicitly permits migration
tests to drop/recreate tables. Tests never fall back to DATABASE_URL or load a .env
for migration connections. Use an exclusive disposable database, never shared data;
parallel pytest workers are rejected. Tests use transaction rollback for synthetic rows.

From the repository root, these commands create a separate local test environment of
the same one-database architecture. The credential is deliberately synthetic:

```sh
export POSTGRES_DB=learner_local_test
export POSTGRES_USER=adaptive
export POSTGRES_PASSWORD=sprint1_test_only
export POSTGRES_PORT=15432
docker compose -p nlp-sprint1-local-tests up -d --wait db
export TEST_DATABASE_URL=postgresql+psycopg://adaptive:sprint1_test_only@127.0.0.1:15432/learner_local_test
export ALLOW_TEST_DATABASE_RESET=1
sh scripts/check_backend.sh
```

For individual checks, from apps/backend:

```sh
uv run --locked pytest -m 'not integration'
uv run --locked pytest -m integration
uv run --locked pytest tests/migrations
DATABASE_URL="$TEST_DATABASE_URL" MIGRATION_DATABASE_URL="$TEST_DATABASE_URL" uv run --locked alembic check
```

After verification, from the repository root, remove only that disposable environment:

```sh
docker compose -p nlp-sprint1-local-tests down --volumes
unset TEST_DATABASE_URL ALLOW_TEST_DATABASE_RESET POSTGRES_DB POSTGRES_USER POSTGRES_PASSWORD POSTGRES_PORT
```

Tests cover UUID/UTC conventions, age/grade bounds, nullable login, uniqueness and
history, many-to-many grants, educator expiry, every FK deletion action, notice content
integrity, consent scope and append-only behavior, optimistic conflicts, empty-to-head
and baseline-to-head upgrades, exact head count, role-only seeding, and schema drift.
Alembic check compares tables/columns/indexes and server defaults. Dedicated tests also
inspect constraint names and exercise trigger behavior because Alembic autogeneration
does not cover every CHECK/trigger change.
