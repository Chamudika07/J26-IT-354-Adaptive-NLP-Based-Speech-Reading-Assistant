# Component 4 live mobile boundary

The existing three role screens accept an optional `liveConnection` prop. When
present they offer an explicit Live/Demo choice. Default launch remains Demo Mode.
Step 297 adds a feature-owned authenticated host and authorized learner selector;
see [ACCOUNT_SESSION.md](ACCOUNT_SESSION.md). It supplies this interface without
pasted JWTs or production response fixtures. Remember Me uses SecureStore as
documented in ACCOUNT_SESSION.md.

## Host integration contract

Supply a stable `LiveConnection` from the host's authenticated state:

- `baseUrl`: trusted HTTPS root ending in `/api/v1`, with no embedded credentials,
  query or fragment. No certificates, firewall rules or endpoint settings are changed.
- `learnerId`: UUID selected through the shared authorized Learners workflow, never
  a demo identity or a claim inferred from a session identifier.
- `role`: current requested display role. This controls client routing, not access;
  the backend independently authorizes the learner and relationship on every call.
- `session.scopeKey`: a nonsecret scope identifier changed whenever the account or
  authenticated session changes. Do not use a token as this key.
- `session.getAccessToken()`: host-owned current token lookup. Null means sign-in is
  required. Access tokens stay in memory; refresh credentials may use SecureStore. Tokens are never logged.
- Optional `session.refreshAccessToken()`: host-owned refresh. Called at most once
  following 401. Missing/failed refresh yields sign-in/unavailable state. There is no
  shared mobile refresh implementation predating this feature. The Step 297
  account-session adapter implements the documented backend refresh contract.

Pass the connection into `LearnerProgressScreen`, `GuardianSummaryScreen`, or
`EducatorAnalyticsScreen`, alongside the existing `periodDays`. Keep the connection
object stable between unchanged renders; replace it on account/learner/role changes.
Remove it on logout. Requests abort and visible live evidence is invalidated when
the connection, role, period, selected learner or mode changes. No live results are
written to the existing persistent demo store. Switching explicitly back to Demo
Mode restores its separately labelled workflow, not a fallback after failure.

The Step 297 App entry point mounts the feature-owned account boundary. It supplies
connections after sign-in and explicit authorized learner selection. No shared
backend Auth contract or generated API client is changed. Do not claim end-to-end
iPhone integration based on mocked-transport tests.

## Endpoint mapping

All paths below are relative to `/api/v1/learner-modelling`.

| Existing mobile screen | Endpoint |
| --- | --- |
| LearnerProgressScreen live analytics | GET `/learners/{learner_id}/progress` |
| GuardianSummaryScreen live summary | GET `/learners/{learner_id}/guardian-summary` |
| EducatorAnalyticsScreen live analytics | GET `/learners/{learner_id}/educator-analytics` |
| Learner live upstream-session action | POST `/reading-sessions` |

GETs use an explicit UTC half-open reporting window of 7/30/90 days, ending at
request time. Reporting boundaries in the response must match the request.
Requests have a 15-second deadline including token lookup, at most one host token
refresh and no automatic retries for provider/network failures. Caller cancellation
aborts requests; user retry is explicit. Responses over 2 MB of declared bytes or
2 million decoded characters are rejected. Fetch buffers the body before the
decoded-size check; this is not a streaming memory limit on React Native.
Only documented 200/201 success statuses are accepted. HTTPS trust uses the device
trust store without certificate bypasses; physical reachability remains unverified.

The schemas in `component4Schemas.json` were exported locally from the current
backend Pydantic contracts: LearnerProgressProjection, GuardianSummaryProjection,
EducatorAnalyticsProjection, ReadingSessionIngest and SessionIngestReceipt. They
contain definitions, not learner records. `validateContract.ts` implements the
schema features these contracts currently emit; regenerate/review the snapshot and
validator when a backend contract changes. `liveProjectionFixtures.json` lives only
under tests and contains synthetic results generated by actual backend projectors.
It is never imported by the production live provider.

## Presentation mismatch resolved without fabricated fields

The old `DashboardPreview` requires non-null metrics and a recommendation. Backend
projections allow null measurements and intentionally contain no advisory decisions.
Do not force those projections into that demo-only shape. `LiveDashboard` instead
preserves missing values, role-specific support history, limitations and separate
contexts. Existing role screens render this in their Live branch with compact cards;
their Demo branch, navigation, scenarios, settings, saved AI report and PDF remain
unchanged. Learner Home/Profile demo observations are not relabelled as live data.

Accuracy proportions become percentages and hesitation rates become per-100 units;
WPM is unchanged. These are display conversions, not analytics calculations.
First/latest values and explanations come from the backend; no new trend,
recommendation, session-history timeline or engagement value is synthesized.
Recorded-session counts are not labelled completed-session counts. Difficulty
observations are not a full reading-session list.

The Learner progress projection does not provide a raw per-session history or
authoritative profile/preferences. Those features are not fabricated by this adapter.
No recommendation or AI generation endpoint is available here. Live rendering shows
that limitation; it never mixes the saved Qwen3 January evidence into live results.

## Submission boundary

The host may supply `pendingSession: ReadingSessionInput` from an approved upstream
measurement workflow to the Learner role screen. The user must explicitly press
Submit Reading Session. The client validates the existing raw-count/duration schema,
learner identity consistency, timestamps and invariants without computing metrics.
The minimized receipt is validated and its client session identity must match.
After acknowledgment the report is re-fetched. A timeout/cancellation does not prove
that a POST failed to persist; retain the same client session ID for an exact retry.
200 means already received, 201 means newly received, and 409 is a conflict.

The current synthetic Reading Results form and scenarios do not populate this prop
or submit to the backend. Final Speech/Adaptive Reading measurement mapping remains
pending. No real learner data was submitted during implementation.

## Blocking/error behavior and iPhone verification

- 401: sign in again after at most one host refresh attempt.
- 403 consent_required: explain learning-support consent is needed; no data shown.
- Other 403: access denied; 404: learner unavailable to this account.
- 409: conflicting retry; 422: check request; 503/network/timeout: unavailable.
- Invalid JSON, wrong role shape, unknown fields, wrong units or wrong reporting
  period: unverified response, never sample fallback.

Backend consent remains deny-by-default. The current authenticated routes cannot
successfully read/write learner evidence until the approved evaluator is integrated.
There is no mobile consent bypass. Missing Guardian/Educator relationships stay denied.

After host authentication/learner selection and trusted HTTPS are available, open
each role screen, explicitly choose Live Mode, verify the consent/access-denied
states first, then (only with approved consent) loading/empty/data/retry/cancel.
Change accounts, learners, roles and periods and confirm no previous evidence is
retained. Test upstream submission/identical retry and refresh using synthetic test
accounts in an authorized environment. Return to Demo Mode and verify saved profile,
preferences, feedback, scenarios and the separate AI report/PDF. This physical-device
verification has not been performed in this step.
